## 结果摘要

- 500 条记录的同步耗时：**约 70 秒 → 1.5 秒**
- 在不水平扩容的情况下，同步量提升约 10 倍
- 死锁概率降低，并发更新行为更可预期
- 1200+ 行的单体处理服务拆分为按数据源划分的策略实现

## 项目背景与约束

Spring Boot 3 / Java 17 体育数据集成平台，负责将外部比赛数据同步到下游服务。随着流量增长，数据接入链路成为主要瓶颈：HTTP 轮询、逐行持久化和高度耦合的业务逻辑导致吞吐不足、锁竞争和运维风险上升。

目标不只是提速，而是让同步链路具备可扩展性、可靠性和可维护性。

## 原始问题

- **数据库往返过多**：记录逐条处理，一次 500 条的同步需要 70 秒以上，大部分时间消耗在重复的数据库交互上。
- **N+1 持久化模式**：去重与更新逻辑逐条查询、逐条更新，带来额外延迟和锁竞争。
- **索引缺失**：用于身份匹配的关键字段没有合适索引，导致全表扫描，并在并发负载下增加死锁风险。
- **单体处理逻辑**：十余个外部数据源由同一个 1200+ 行的服务处理，清洗、映射、合并和持久化混在一起。

## 根因分析

性能问题的主因不在硬件，而在数据访问模式：逐行写入放大了网络和数据库开销；缺失索引让去重路径退化为全表扫描并拉长锁持有时间。单体服务则让每次修改都牵一发而动全身。

## 技术方案与关键取舍

1. **批量 Upsert**：以 MyBatis 批量操作配合 MySQL `INSERT ... ON DUPLICATE KEY UPDATE`，将数百次写入合并到单个事务中。
2. **索引设计**：对去重关键路径做性能剖析，增加用于身份匹配的复合唯一索引，消除全表扫描、缩短锁持有时间。
3. **策略模式拆分**：按数据源拆分为 Strategy 实现，替代 1200+ 行的单体服务，新增数据源时只需新增策略。
4. **可观测性与测试**：MDC Trace ID 贯穿请求链路；日志采样防止日志风暴；基于 Testcontainers 的集成测试；定时任务与测试启动隔离。
5. **传输方式调整**：在合适的链路上，将反复的 HTTP 轮询改为基于 WebSocket / MQTT 的长连接推送，缓解数据源限流并提升数据新鲜度。

取舍：优先消除架构瓶颈，而不是增加基础设施容量。

## 验证方法

通过基于 Testcontainers 的集成测试验证改动，并借助 MDC Trace ID 做端到端链路追踪。性能数字的测试环境及测量条件未公开。

## 最终结果

| 指标 | 结果 |
| --- | --- |
| 500 条记录同步耗时 | 约 70 秒 → 1.5 秒 |
| 同步量 | 不水平扩容的情况下提升约 10 倍 |
| 可靠性 | 死锁概率降低，并发更新更稳定 |
| 可维护性 | 单体服务拆分为模块化处理组件 |

## 适用场景与工程价值

适用于存在逐行写入、N+1 查询、索引缺失或多数据源耦合问题的数据接入 / ETL 系统。核心方法是先定位数据访问模式上的瓶颈，再以批处理、索引和模块化改造解决，而不是直接扩容。
