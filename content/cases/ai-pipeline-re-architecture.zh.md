## 结果摘要

- 单次运行（约 500 条记录）：**约 160–180 分钟 → 约 8 分钟**（约 16–22 倍）
- LLM 成本：约 $15–20/天（等价）→ 约 $0.13/次运行
- 单条输入载荷：约 8KB → 约 500B（约减少 93%）
- 无效记录进入死信路径并告警，不再中断整条流水线

## 项目背景与约束

一个已在生产中使用、并已证明业务价值的 AI 工作流：采集体育赔率与历史数据，生成 AI 预测与分析，写入 MySQL，并向下游分发报告。每次运行约 500 条记录。小规模时运行正常，规模上来后性能和运行成本成为主要约束。

## 原始问题

- 每条记录一次 AI 请求（N+1 模式）
- 输入载荷过大，token 消耗高
- AI 处理后元数据丢失
- 数据库写入失败、限流压力大
- 凭据在容器重启后失效

即使升级硬件和模型，工作流仍难以扩展。

## 根因分析

问题不在模型能力，而在数据流架构：

```text
一条记录 → 一次 AI 请求 → 一次数据库操作 → 重复 500 次
```

每一层都引入了不必要的串行化、同步和网络开销，无论模型多强，吞吐都会受限。

## 技术方案与关键取舍

1. **批处理**：将比赛记录按约 20–25 条分批送入 AI 流水线，网络往返减少约 95%，同时降低限流风险。
2. **输入压缩**：增加专门的 ETL 层，只保留球队信息、联赛元数据、比赛时间和核心赔率数据，单条载荷由约 8KB 降至约 500B。
3. **按负载路由模型**：常规记录使用高吞吐模型，复杂记录使用高级推理模型，以成本和任务复杂度而非便利性选择模型。
4. **数据血缘保持**：AI 处理后 `match_id` 等标识可能丢失；改为 AI 处理分支与元数据分支并行，再做确定性合并，保证引用完整性。
5. **死信队列**：先校验，无效记录进入死信路径并通过 Telegram 告警，正常记录继续处理。另外补充了工作流状态持久化、显式密钥管理，以及凭据在容器重启后的持久化。

## 验证方法

以单次运行耗时、LLM 成本、载荷大小和失败处理方式进行改造前后对比，见下表。两项成本数字计量单位不同（按天 / 按次运行），不宜直接换算为百分比。

## 最终结果

| 指标 | 改造前 | 改造后 |
| --- | ---: | ---: |
| 单次运行耗时 | 160–180 分钟 | 约 8 分钟 |
| 提速 | - | 约 16–22 倍 |
| LLM 成本 | 约 $15–20/天（等价） | 约 $0.13/次运行 |
| 单条载荷 | 约 8KB | 约 500B |
| API 调用模式 | 逐条请求 | 批量处理 |
| 失败处理 | 流水线中断 | 死信队列 + 告警 |

## 适用场景与工程价值

多数 AI 工作流的问题不是模型质量，而是数据流设计。本案例的方法——批处理、输入裁剪、模型路由、血缘保持、失败隔离——可直接用于 LLM 基础设施、Agent 编排、工作流自动化和数据平台。
